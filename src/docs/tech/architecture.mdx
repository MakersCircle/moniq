# System Architecture

`moniq` is designed to be a lightweight, serverless (or "bring your own storage") application. 
To prioritize privacy and simplicity, it leverages the user's personal Google Drive via **Google Sheets** as the primary datastore, protected by **Google OAuth.**

## High-Level Architecture

### Characteristics

- **Frontend:** Single Page Application (React / Vite). Mobile-first, Progressive Web App (PWA) ready.
- **Backend:** Serverless, driven by direct Google Sheets API calls over HTTP.
- **Authentication:** Google Sign-In (OAuth 2.0).
- **Database:** Google Sheets API. Each user gets a "moniq" folder created in their Drive on first login, containing a "Moniq Database" spreadsheet.

## 🗄 Database Schema (Google Sheets Outline)

Instead of a traditional SQL/NoSQL database, `moniq` uses Tabs in a Google Sheet — six data tabs plus one internal metadata tab (`SHEET_NAMES` in `src/sync/types.ts`; column lists in `src/schema/entities/*.schema.ts`). Every data sheet ends with `Is Deleted`, `Created At`, `Updated At`, and `Checksum` columns (soft-delete, timestamps for conflict resolution, and a row-integrity hash), omitted below for brevity.

### 1. `Accounts` Sheet
Stores all custom accounts, wallets, etc. These are the source of truth for money.
- `ID`, `Name`, `Type` ("Asset" | "Liability"), `Description`
- `Is Savings` (Boolean), `Initial Balance` (Number), `Exclude Net` (Boolean — excludes this account from Net Worth calculations)
- `Is Active` (Boolean)

### 2. `Methods` Sheet
Stores payment channels (abstractions over accounts).
- `ID`, `Name`, `Linked Account ID` (UUID of Account)
- `Is Active` (Boolean), `Sort Order` (Number — user-controlled drag-to-reorder position)

### 3. `Categories` Sheet
Holds headers and subheaders for tracking.
- `ID`, `Group` ("Income" | "Needs" | "Wants" | "Invest" | "Lend" | "Borrow"), `Head` (e.g. "Food"), `Sub Head` (e.g. "Groceries")
- `Initial Balance` (Number — opening balance for Invest/Lend/Borrow-style categories), `Is Active` (Boolean), `Sort Order` (Number)

### 4. `Transactions` Sheet
The core event log based on a **Double-Entry Ledger System**.
- `ID`, `Group ID` (UUID — note: each transaction, including each line of a split, gets its own independent Group ID; they are not linked into one shared group), `UI Type` ("income" | "expense" | "transfer")
- `Entries JSON` (Balanced `LedgerEntry[]`: `[{ accountId, type, amount }]`), `Amount` (Number), `Date` (ISO date string)
- `Method ID`, `Note`, `Tags` (comma-separated string)

### 5. `Budgets` Sheet
Per-category monthly allocations.
- `ID`, `Category ID` (UUID of Category), `Period` (String, `"YYYY-MM"`), `Amount` (Number)

### 6. `Settings` Sheet
A simple key/value store for user preferences (currency, locale, date format, fiscal year start month, etc.).
- `Key`, `Value`

### `_meta` Tab (internal)
Not a data sheet — holds the schema version (`schema_version` key) used by the migration system (see below), separate from user-facing Settings.

## 🔌 API & Integration Layers

### 1. Google OAuth Authentication
- Scopes: `email`, `profile`, `drive.file`
- The app only accesses files it created itself.

### 2. State Management & Sync (Client-Side)
- **Local Storage:** `zustand/persist` with a custom IndexedDB adapter (`idb` library).
- **Optimistic UI:** Mutations update the Zustand store immediately. The SyncEngine debounces writes (3s window) before flushing.
- **SyncEngine:**
  - **Pull:** Reconciles local vs remote using `updatedAt` timestamps.
  - **Push:** Groups dirty operations by entity type. Uses `append` for new rows and `batchUpdate` for existing rows.
  - **Conflict resolution:** If a row's checksum doesn't match what Moniq last wrote (i.e. someone manually edited the sheet), the remote row unconditionally wins. Otherwise, whichever side has the newer `updatedAt` wins; on an exact tie, remote wins.

## 🗂 Schema Versioning & Migrations

Moniq tracks a schema version (`CURRENT_SCHEMA_VERSION` in `src/schema/version.ts`) for both IndexedDB and the Google Sheets database, so the on-disk/on-sheet shape can evolve safely across app versions.

- **Migration runners:** separate runners for IndexedDB (`src/schema/runner/idbMigrationRunner.ts`) and Sheets (`src/schema/runner/sheetsMigrationRunner.ts`), each applying versioned migration steps in order.
- **Safety backup:** before running a Sheets migration, the engine takes a dated backup copy of the spreadsheet first, so a failed or buggy migration can be recovered from.
- **Sync status:** while a migration is running, `SyncEngine` reports a `'migrating'` status and gates all writes — no data is flushed to the sheet mid-migration.
- **Multi-tab coordination:** `src/schema/runner/migrationChannel.ts` broadcasts migration start/end across open tabs (via `BroadcastChannel`), so only one tab runs a migration at a time and others wait rather than racing.
